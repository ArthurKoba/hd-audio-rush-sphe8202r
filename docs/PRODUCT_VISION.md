# Целевой продукт HD Audio Rush 5.1: S/PDIF + Bluetooth + Wi-Fi

Этот документ описывает **зачем ведётся весь reverse engineering SPHE8202R** и какой самостоятельный порт мы хотим получить. Это **целевое состояние**, а не утверждение о реализованной прошивке. Текущая техническая работа ведётся в [Issue #43](https://github.com/ArthurKoba/hd-audio-rush-sphe8202r/issues/43) и [USB Issue #48](https://github.com/ArthurKoba/hd-audio-rush-sphe8202r/issues/48).

## 1. Практическая проблема

TV-приставка передаёт HDMI audio passthrough на телевизор, телевизор выдаёт коаксиальный S/PDIF, а SPHE8202R декодирует/обрабатывает его и формирует многоканальные выходы. Приставка в этом режиме не меняет громкость S/PDIF-потока — привычные кнопки громкости не управляют итоговым уровнем звука.

```text
TV-приставка -- HDMI passthrough --> TV
                   (звук)            |
                                     | coax S/PDIF
                                     v
                              SPHE8202R + DSP
                                     |
                              выходы 5.1 / усиление
```

**Обязательная продуктовая задача** — когда пользователь нажимает Volume Up / Volume Down / Mute на TV-приставке, передать управление **по Bluetooth в конвертер** и менять **мастер-громкость непосредственно в SPHE/DSP**, не изменяя физический S/PDIF-аудиопуть. Передача аудио по Bluetooth не нужна для достижения основной цели; SPDIF остаётся предпочтительным звуковым трактом.

**Условие совместимости:** сама возможность Bluetooth-сопряжения не гарантирует передачу кнопок громкости при активном HDMI/S/PDIF. Надо проверить, какой режим TV-приставка поддерживает (AVRCP absolute volume, HID или иной реально доступный профиль/интеграция) и может ли он отправлять события/значения на конвертер. Это часть будущей продуктовой приёмки, а не установленный факт.

## 2. Bluetooth: управление поверх S/PDIF

Обязательные целевые функции: сопряжение с TV-приставкой, получение её команд регулировки мастер-громкости и mute, воспроизводимая шкала уровня, защита от скачка громкости, устойчивое переподключение. Возможные дополнительные функции — метаданные воспроизведения, статус, отображение уровня и двухсторонняя синхронизация там, где поддерживается выбранный профиль.

Передавать через Bluetooth сам многоканальный звук, Dolby/DTS либо разрабатывать Bluetooth SCO не требуется для первого работоспособного продукта. Эти функции не должны блокировать управление громкостью.

## 3. Wi-Fi: DSP-dashboard и мониторинг

Целевые функции веб-интерфейса:
- Настройка АЧХ/эквалайзера и DSP-алгоритмов, индивидуальных уровней каналов, баланса и пространственной сцены, сохранение профилей.
- Статус аудиовхода, формат/режим, мастер-громкость, аппаратные ошибки, пиковые значения, клиппинг и метрики DSP **только если соответствующее измерение действительно доступно или реализовано в новом DSP-коде**.
- Логи, диагностика, при необходимости открытый API для умного дома.
- В дальнейшем безопасный OTA-update с аутентификацией, проверкой целостности и независимой процедурой восстановления при потере питания; штатный SPI-ROM loader пока не равен безопасному OTA.

Wi-Fi может быть единственным первым радио-каналом для dashboard/отладки, Bluetooth — первым для управления громкостью. Разрешён поэтапный результат без обоих интерфейсов одновременно.

## 4. Как подключаем радио

**Приоритетная архитектура: SPHE8202R MIPS + непосредственный USB Wi-Fi, USB Bluetooth или комбинированный USB Wi-Fi/BT-адаптер.** USB Host исполняется на SPHE, драйвер радиочипа и перенесённые сетевой/Bluetooth-стеки также исполняются на SPHE. Второй микроконтроллер **не предполагается**.

У чипа нет готовых драйверов Wi-Fi/BT и сетевого стека в исследованной прошивке. Требуется восстановить USB Host и написать/портировать поддержку конкретного радиомодуля. До покупки адаптера нельзя заявлять ни его USB-совместимость, ни успех подключения.

**Резервный путь:** если прямой USB окажется непригоден, внешний микроконтроллер связи допустим как запасное архитектурное решение. Он не входит в текущий Issue #48 и не отменяет исследование USB.

**Предпочтения реализации:** C — основная база; C++ допустим. Rust сейчас не рассматривается. Код и опыт ESP32/ESP-IDF можно использовать как ориентир по API и архитектуре USB/Bluetooth/сетей **с проверкой лицензии, зависимостей, переносимости на MIPS и аппаратно-специфичных частей**. ESP32 как промежуточный контроллер не нужен для основного варианта.

## 5. Этапы, не смешивать критерии готовности

1. **Исследование USB Host — [Issue #48](https://github.com/ArthurKoba/hd-audio-rush-sphe8202r/issues/48).** Полностью восстановить USB hardware/software contract из исходной прошивки: режимы, EP0, control, bulk, interrupt, при наличии iso, адресация, enumeration, DMA/PIO, IRQ, NAK/STALL, toggle/retry/timeout, параметры endpoint, root/hub/multi-interface, ограничения. Сформулировать возможность написания собственного USB class/vendor-драйвера.
2. **Подготовка C/C++-драйвера.** Разрешены основанные на подтверждённых данных интерфейсы, таблицы регистров, заготовки и host-side unit tests без устройства. Сейчас реального USB Wi-Fi/BT-донгла **нет**, аппаратная приёмка невозможна.
3. **Проверка радио при появлении адаптера.** Добиться аппаратно подтверждённого подключения и обмена **хотя бы по одному** Bluetooth или Wi-Fi интерфейсу; для комбинированного — независимо проверить оба и одновременную работу. Статическое доказательство USB Host не заменяет этот критерий.
4. **После подтверждения хотя бы одного рабочего радио-интерфейса** открывается **отдельный Issue по сетевому стеку / Bluetooth-протоколам и интеграции**. До этого новый Issue **не открывать**. Исследование переносимости стеков предварительно допускается внутри #48.
5. **Самостоятельная прошивка и продуктовая приёмка:** развёртывание USB-драйверов/радиостека, связь TV-приставки с Bluetooth-громкостью, управление DSP, web UI, диагностика, интеграция и безопасный OTA. Это другой этап; сейчас не заявлять работоспособность на реальном процессоре.

Полный реверс CPU, DSP, IOP, аудиопайплайна, USB/UART и аппаратных регистров в [Issue #43](https://github.com/ArthurKoba/hd-audio-rush-sphe8202r/issues/43) необходим как база собственной прошивки и **служит этой продуктовой цели**.

## 6. Где хранится информация

**`main`** — постоянная продуктовая цель и проверенные переиспользуемые исходники/тесты; **#43** — общий reverse engineering и прогресс; **#48** — USB Host и реальная применимость радио-модулей; **канонический Ghidra Analysis `sphe8202r_decoder_p25d80`** — машинные доказательства и аппаратная семантика. Тело тематического Issue — задача и критерии, подробные завершённые исследования — в содержательных комментариях. Без параллельных локальных аналитических отчётов.

Оригинальные прошивка/дамп неизменяемы; до отдельного решения — никаких записей в SPI Flash или сборки продуктового образа.
